# Airbnb alteration intake

VAY-1551, 2026-09-08. Builds on `airbnb-request-decisions.md`.

## Scope

An alteration's `payload.bms.booking_id` identifies an existing Channex booking.
Unlike reservation requests, intake needs no speculative future-booking match or
host-response deadline. Use the documented booking-revision attributes for the
proposed dates, room occupancy and total. Missing total is unknown, not zero.

Store the request in `booking.booking_change_requests`; retain provider identity
and normalized context in `requested_changes.channex`. The local request ID is
generated by Vayada. No raw message, card data or guest contact is copied.
An expression index enforces one row per provider live-feed event ID.

Only a connected, active Channex binding and an unambiguous same-property Airbnb
booking mapping can admit a request. The intake call carries the expected binding
generation from the queued job; reject a changed binding. Do not match on guest,
dates, public reference or a local ID that happens to resemble a provider ID.

Preserve the original booking snapshot on replay. Duplicate requests cannot
overwrite a proposal or reopen a locally/provider resolved request. A changed
proposal under the same provider event ID is an evidence conflict for review.
Never copy an arbitrary webhook body directly to the intake: the future worker
must pull the live-feed event from Channex and validate its property and identity.

## Activation and downstream work

The first intake slice is callable by tests only, not registered in server.ts.
Before enabling it, the subsequent provider worker and PMS integration must:

- Show before/after dates, guest counts and nullable monetary values.
- Route both decisions through a durable, property-authorized command; prohibit
  the direct Booking Engine accept/decline implementation for these records.
- Verify availability without counting the booking's own allocation twice.
- Keep the existing booking untouched until an authoritative modified revision
  arrives; reconcile declines/withdrawals by live-feed reads without a webhook.
- Preserve actor/time, reject opposite intents and reconcile unknown POST results
  before resending; keep sent-but-unconfirmed distinct from applied.
- Pass authorization, PostgreSQL, revision, worker and PMS browser tests.

No provider deadline is inferred. The missing reservation-request fixtures block
VAY-384 activation, but do not prevent this separately testable alteration intake.
Real Airbnb end-to-end acceptance still needs sanctioned provider fixtures and
an authorized connection; shared Booking.com/OpenChannel fixtures do not qualify.

Provider reference: [Channex Airbnb API](https://docs.channex.io/api-v.1-documentation/airbnb-api#alteration-request).

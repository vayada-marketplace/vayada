_VAY-2499 reference for the [AI actions design note](ai-actions-design-note.md). Built from the
code at commit `e0659e30d` (2026-11-18). Every row links to the line it comes from; line numbers

This file lists every place in `apps/api` (and the shared auth packages it calls) where authority
is decided **outside** the route's `enforceRoutePolicy` check. A delegated AI request
(design note [§5](ai-actions-design-note.md#5-delegation-acting-as-the-user)) passes the route
check with the user's own permissions, so each place below either refuses delegation by default
(sections A to D) or must be taught about it before any write action reaches it (section E).

## A. Owner-session gates

A route treats `context.actor.providerIdentity.sessionId` as proof that the account owner is in a
first-party browser session. The resolver fills it from the token's `sid`
([`resolve.ts:100`](../packages/backend-auth/src/resolve.ts#L100)). On an MCP token `sid` is a
WorkOS consent id, so a delegated context **never** carries a session id
(design note [§5.2](ai-actions-design-note.md#52-the-delegated-context)) and every gate below
refuses it. None of these routes is in the action catalog.

## E. In-transaction permission re-reads

The command re-reads the caller's membership and permissions inside its own transaction instead
of trusting the request context. A delegation that narrows the user's rights (read-only, fewer
properties) is invisible to these reads, so **each site a write action reaches must take the
delegation as input before that action is registered**
(design note [§5.4](ai-actions-design-note.md#54-write-delegation-through-authority-sites)).

There are two kinds, and they need different fixes:

- **Effective-permission re-reads** resolve role grants, team-role definition, overrides and
  property assignment like the route does. Delegation can narrow their result.
- **Role-grant joins** join `identity.role_permission_grants` on the membership's `role_key`.
  They see neither team-role definitions nor per-member overrides, so they pass any member whose
  base role holds the key.

### What this means for the first write batches

The commands in `pmsOperationsCommandRepository.ts` (notes, room blocks, room moves, check-in,
check-out) do **not** re-read permissions in their transaction, except room type retire; they rely
on the route check, which the delegated context already narrows. The re-reads a P4/P5 action does
hit are:

- `lockPmsInboxRolePermissions`: thread done / follow-up / reopen, replies;
- `lockReplacementPricingAuthorization`: bulk prices through pricing-v2;

## F. Never-list routes

Every `apps/api` route behind each never-list item in design note
[§6](ai-actions-design-note.md#6-the-never-list): 176 rows. A route can sit under two items; it
is listed under both, marked "also F*n*".

Which rows an action may call:

- **Never:** every non-`GET` route in F; every route in F7 (staff), F12 (platform), F13 (GDPR),
  F14 (auth), F18 (maps resolver) and F20 (owner-only, later); and the reads the design note
  deny-lists ([§3.2](ai-actions-design-note.md#32-projections)).
- **Only with a projection that drops the listed data:** `GET` routes in F16 (ID documents: drop
  every document field) and F19 (`platform.*` rows: drop every field taken from them). This is how
  `channel_alerts_list` and the in-app thread read stay allowed.
- **Context only:** the other `GET` routes (plan status, payout list, payment settings,
  cancellation policy and the like). They sit in a never-list area, but the plan does not list the
  read itself. No action in the current catalog calls them; adding one is a registry decision
  that must keep bank details, payout destinations and billing data out.

included) into 482 mounted routes and searching their paths per item, then reading each route.
Many routes exist only when a runtime option is set (vayada Payment, admin transfer,

#### Notes on the never-list routes

- **AI connections do not exist yet**: no connection, MCP or OAuth-client code is in
  `apps/api/src`. Their management routes join F14 when VAY-2513 adds them.
- **No route deletes a hotel account.** F8 has the two property-deletion routes, the signed-in
  user's own GDPR deletion, and platform routes; the platform property `DELETE` always answers 409.
- **Several never-list writes are not owner-only today**: payment-settings `PATCH`,
  payment-windows `PUT`, Stripe reconcile, Xendit payout reconciliation, folio finalise and
  delete, guest merge and the no-show report `POST`; finance exports start with only
  `pms.finance.read`. The never-list is the AI's guard for them, not an owner gate.
- **F10** includes the Airbnb import start and complete routes next to Channex connect, because
  they create a Channex-hosted Airbnb connection.
- **F3** includes the public guest confirmation route because it shows the hotel's bank details to
  the guest. It is not a hotel-facing route; it is listed so no AI wrapper reuses it.
- **F19** lists hotel-facing reads whose answers carry values from `platform.jobs`, `domain_events`,
  `product_audit_events`, `dead_letter_events` or `external_webhook_events`. Write routes that
  return only the job they just queued are not listed.
- `GET /api/booking/hotels/:hotelId/reservations` returned passport numbers, dates of birth and
  gender unmasked until VAY-2562 removed them from the list, so it is no longer in F16; see design
  note [§3.2](ai-actions-design-note.md#32-projections) for what it still returns.

## G. How to refresh this inventory

Count first, then read every hit; never cut a list with `head`. Run from the repo root.

```bash
# A. owner-session gates
grep -rn --include='*.ts' 'providerIdentity.sessionId' apps/api/src packages | grep -v '\.test\.ts'
# B. ownerOnly route policies
grep -rn --include='*.ts' '{ ownerOnly: true }' apps/api/src | grep -v '\.test\.ts'
# C and D. hotel_owner in TypeScript (comparisons are C, SQL strings are D)
grep -rnw --include='*.ts' hotel_owner apps/api/src packages | grep -v '\.test\.ts'
# D. owner checks left in database functions (expect only grants and 0205 guards)
grep -nw hotel_owner packages/backend-migration/migrations/*.sql
# E. permission re-reads: any file that row-locks identity tables or reads role grants
grep -rlw --include='*.ts' -E 'role_permission_grants|permission_overrides' apps/api/src packages | grep -v '\.test\.ts'
grep -rn --include='*.ts' -E 'lockMemberPermissions|lockPmsInboxRolePermissions|lockHotelSetupMembership|lockPmsManageScope|lockHotelSetupOwnerAuthority' apps/api/src | grep -v '\.test\.ts'
```
